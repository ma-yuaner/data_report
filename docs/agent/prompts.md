# 项目任务模板

用途：减少遗漏业务粒度、流程和验收。按当前任务选一个模板，把已知内容填入；不用每次粘贴所有模板。先遵循根AGENTS.md和最新用户指令，模板不创建额外审批流程。

角色可以直接点名：明策（产品）、绘景（UI）、星桥（前端）、磐石（后端）、明鉴（QA）。[能力卡与使用回执](roles/README.md)说明各自能力和增强方式。点名采用该角色视角，不等同于要求启动独立子代理；需要独立执行时明确说“启动某角色的独立子代理”。

增强示例：“加强明鉴：以后针对数据页面，必须检查NULL/0、部分同步和筛选条件继承；把要求更新到明鉴能力卡并记录版本。”交付需报告实际使用角色和产物，明确独立子代理是否启动。

## 1. 需求与业务闭环讨论

```text
在data_report项目继续，先读docs/agent/README.md及当前工作流。
本次只做方案。业务问题：……；当前真实例子：……。
请核对现有代码和数据契约，分别写出已实现、演示、缺口。
给出数据读取、清洗、指标、页面、异常、人工决策、技术回传、效果复盘的衔接。
列明粒度/时间/公式、角色与状态、所需字段、已有表复用及新增理由。
把前置依赖、待确认项和分阶段验收写入方案；提最影响本轮决策的问题。
不能把建议阈值、效果归因、部署状态当作已确认事实。
```

## 2. 用真实数据分析一次调整

```text
课题：白名单/MPIS调整后查定比变化。变更时间：……；范围：……。
先校验请求、出票航段和同步批次，再比较同范围/同星期/完整业务日。
拆MP普通、NDC、MPIS的绝对请求量与占比；拆出票航段变化和配置归属。
仅对已具备航段分母的粒度算比率，航线仅分析现有三阶段质量。
说明事实、可验证假设、其他影响及数据缺口，不把相关性直接认定为原因。
输出SQL/来源、对账、核心结果、证据、待补字段和下一步；未经要求不发消息、不执行控制动作。
```

## 3. 按已确认范围开发

```text
本轮批准范围：……；方案路径/版本：……；验收例子：……。
核对仓库和现有改动，复用已有事件、通知、工单和UI组件。
按docs/product/product-delivery-contract.md实现涉及的页面/API/权限/数据契约。
ETL或DDL需配合的先列出；只改授权范围，不修改公共连接配置。
对状态、缺失/0、筛选传递、重复运行和权限做与风险相称的测试。
交付修改内容、验证结果、SQL/调度顺序、回退方式和下一步，更新项目记忆与工作流。
完成本地验证后按仓库约定直接推送两端，报告提交与推送结果；默认不查询或等待CI，部署状态单独报告。
```

## 4. 页面与组件产品评审

```text
页面/用户角色：……；最重要的操作：……；原型/现有组件：……。
先画信息层级和主路径，列字段标签、控件、默认值、必填规则、帮助文案。
检查空态、加载、异常、权限、保存反馈、取消/重试、抽屉层级和横向滚动。
确认筛选是手动查询还是即时生效，以及哪些条件必须传入下钻。
用一个正常例子和一个失败/缺数据例子验收；演示数据与真实数据明确区分。
```

## 5. 端到端验收与交接

```text
验收范围与环境：……；只用隔离测试对象/获准数据。
逐段核对源数据→清洗→页面→规则→事件→通知→处置→技术回传→效果验证。
每段记录输入键、批次/版本、预期、实际证据和清理方式。
“调度成功但读取0”“到期但未恢复”“通知已发送但未执行”等分别判断。
给出通过、未通过、未验证清单及下一步；更新docs/agent/workstreams.md。
```

## 6. 明策维护项目README

```text
明策，请按当前代码更新README：核对实际菜单及层级、全部后端接口、启动配置和已实现/演示/预留状态。
运行python scripts/check_readme.py --write同步菜单/API目录，再用--check核验；产品说明与专题链接人工复核，代码存在不写成已部署或已验收。
保持入口简洁，完整接口放docs/api/README.md；说明变化和检查结果，更新工作流后提交推送两端，不查询或等待CI。
```

## 7. 明策高级产品经理需求与优化（v3）

对应[明策v3能力卡](roles/product.md)。只需提供已知信息，不必先写完整需求文档；不知道的填“待核对”。普通任务用简短版，复杂或跨层需求再用完整版。方案、开发和效果验收是不同范围，不要一次混写成全部已授权。

### 简短版：下次直接这样问

```text
明策，请按高级产品经理标准梳理【模块/需求】，本次先做方案，不开发、不操作数据库。
给谁用：【用户/岗位】；当前问题：【真实例子或不方便的地方】。
希望达到：【预期结果】；约束：【已知时间、数据、权限或范围限制，没有则待核对】。
请先核对现有代码与业务契约，给出需求判断、推荐方案、优化前后效果、开发顺序和验收标准。
区分已实现、演示、预留与缺口，另列部署/数据/验收状态；缺依据的收益和指标不要编造。
优先问最多3个影响决策的关键问题，其余标注假设；先给简短结论，再展开必要细节。
```

### 完整版：复杂需求或跨模块优化

```text
明策，请在data_report项目按你的v3能力卡，以高级产品经理标准设计【模块/需求】。
先读docs/agent/README.md、当前工作流、明策能力卡及相关业务契约和代码。
本次范围：只讨论方案，不修改业务代码、不执行数据库/通知/生产操作；是否保存方案文档：【否/指定路径】。

已知背景：
- 目标用户与场景：【谁、什么时候、要完成什么任务】
- 当前问题与真实例子：【操作路径、症状、频率、影响；可附截图或工单】
- 希望达到的结果：【想改善的决策、体验或业务结果；未知基线不硬填数字】
- 已知约束：【日期、数据范围、权限、依赖、必须兼容项；没有则待核对】

请交付：
1. 问题判断与目标：区分症状、待验证原因和解决办法，说明是否值得开发；列目标指标、基线、观察期、来源与护栏。
2. 现状与缺口：按代码/契约证据盘点已有、演示、预留、可复用与待新增能力，部署、数据就绪和验收另列。
3. 方案与取舍：有实质决策时比较最小改动与扩展方案，必要时包含暂不开发；说明推荐理由、本轮必须、下一阶段、后置及排除项。
4. 优化前后：逐项列当前问题、拟议变化、用户可见效果、验证方法、代价和风险，不把预期写成实测收益。
5. 可开发的轻量PRD：主路径、菜单/页面、字段、筛选/下钻、操作、状态、权限、异常与数据/API要求；按相关性覆盖，不适用项说明。
6. 交接与顺序：绘景/星桥/磐石/明鉴分别需要什么输入、产出什么；列DDL、ETL、生产配置等依赖和待指定负责人，不声称已调用角色。
7. 验收与复盘：正常、无数据、部分同步、越权、重复操作、失败/恢复例子，分阶段启用和回退要求，以及后续用什么证据判断效果。
8. 待确认：优先集中提出最多3个影响本轮决策的问题，其余假设标注；关键口径或权限未确认不擅自定案。

先给结论与推荐范围，再按必要程度展开；不虚构收益、工期、数据、部署或验收结果，不为小改动强制长篇PRD。
```

### 同一需求的后续追问

- 评审取舍：“明策，评审刚才方案的必要性、最小范围、数据可行性和遗漏风险，给出保留/调整/后置项，暂不开发。”
- 授权开发：“批准【方案路径/版本】中的【明确范围】开发，排除【不做项】；按【验收例子】实现和验证，完成后按项目约定推送两端。DDL、生产操作与外部通知未授权。”完整交付要求可用[开发模板](#3-按已确认范围开发)。
- 验证效果：“明策，按【方案/指标】复盘【时间窗与范围】，使用【获授权的数据/证据】对比优化前后，区分预期、实测、未验证和其他影响；缺基线先列采集方案，不执行生产动作。”

只说“先设计方案”不会自动授权业务开发；明确批准开发后直接推进已批准部分，不重复索要同一授权。跨会话时补充方案路径/版本，不假设能恢复未保存的讨论。
