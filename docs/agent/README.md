# 企业数据中台项目协作入口

更新：2026-10-20。此目录是随Git版本管理的项目记忆与知识入口，不是运行中的业务数据库或自动学习服务。

## 开始一项工作

1. 确认仓库、分支和已有改动；应用与ETL使用各自仓库。
2. 读根目录 [AGENTS.md](../../AGENTS.md)、[项目记忆](memory.md)、[当前工作流](workstreams.md)。
3. 从 [知识索引](knowledge-index.md) 进入相关业务、数据契约、代码；重要已确认规则查 [决策记录](decisions.md)。
4. 按 [产品交付规范](../product/product-delivery-contract.md) 明确问题、数据和验收；需要时选 [任务提示词](prompts.md)。
5. 输出事实、推断和待确认项；跨表计算先检查粒度和数据完整性。

## 文档分工

| 文件/目录 | 负责什么 | 维护方式 |
|---|---|---|
| `AGENTS.md` | 简短、稳定的协作规则和阅读入口 | 工作方式改变时更新，不堆业务历史 |
| `memory.md` | 当前稳定背景、常见陷阱、关键路径 | 保持精简；旧细节移入业务文档 |
| `decisions.md` | 用户确认的决策、适用范围、替代关系 | 新决策追加；旧决策保留并标记被替代 |
| `workstreams.md` | 每个项目阶段、阻塞项、下一步和证据 | 每个有实质进展的任务结束更新 |
| `knowledge-index.md` | 外挂资料、仓库文档、代码、SQL的定位 | 写清来源、状态、时效、拥有者 |
| `docs/business/air_ticketing` | 公司业务规则与已实现数据口径 | 与指标、代码变化同步更新 |
| `docs/product` | 需求、方案、字段、状态和验收标准 | 草案、确认、实现、验收分开记录 |
| `prompts.md` | 需求梳理、取数分析、实现和验收的输入模板 | 用真实返工案例改进，不重复系统指令 |
| `roles/` | 明策、绘景、星桥、磐石、明鉴的能力卡与使用回执约定 | 用户明确增强要求后更新对应卡片与版本 |
| `README.md`、`docs/api/README.md` | 项目现状、菜单、完整接口入口 | 明策按能力卡维护，目录块用`scripts/check_readme.py`同步核对 |
| `CONTRIBUTING.md`、`docs/development` | 开发检查、目录依赖、双仓边界和结构迁移记录 | 与工程规则同步更新 |

## 知识如何生效

根目录AGENTS.md提供阅读路由；其他文件按任务读取。开启新会话时，把工作目录选到本应用仓库。若仍在旧`D:\data_team_repo\data-team-repo`目录，应用仓库的AGENTS.md不在该目录的指令路径上，不能假设自动加载；应切换项目目录或明确要求读取本项目入口。

点名角色或需要增强某个角色时，从[角色入口](roles/README.md)读取对应卡片。名字可以直接用于对话；能力更新保存在Git文档中，角色使用方式在开工、切换和交付时明确报告。

“外挂知识库”当前采用Git中的来源目录和索引。外部Excel、会议纪要、技术文档须先可访问，再记录版本、状态和对应知识条目；链接失效时标记缺失，不凭聊天记忆补造内容。数据库结构以最近核验结果为准，仓库DDL只能证明设计。暂未配置向量检索库、MCP知识服务或自动同步作业，无需先建这些设施才能开展本轮工作。

## 一次交接的最小内容

业务目标、已确认口径、修改文件/提交、验证证据、尚未执行的SQL/调度、待补数据、下一步。提交成功、CI通过、服务器部署、业务验收分别记录，不能互相替代。

官方依据：[Codex项目工作流示例](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)明确区分可识别的AGENTS.md与可自行组织的计划、提示词和上下文文件；这里采用的是本项目约定。
