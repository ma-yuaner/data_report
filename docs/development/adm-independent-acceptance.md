# ADM独立接管：建表、部署和人工验收

2026-10-24。本轮由中台独立管理，新数据写MySQL `sibebid.adm_case_document`，不修改ERP `adm_records`。原子主单JSON保存明细、处理/申诉/审核、附件元数据及审计；生成列只供检索，附件原件在独立持久卷。此为管理首版，不是无限容量或全量旧系统已迁完。

## 1. 你执行的DDL（二选一）

先在数据库工具确认当前实例、备份及MySQL版本，再只读检查：

```sql
SELECT DATABASE(), VERSION();
SHOW TABLES FROM sibebid LIKE 'adm_case_document';
```

- **没有adm_case_document**：执行[新建DDL](../sql/adm-management-center-v1.sql)。脚本明确USE sibebid；只新建中台表和索引，不创建新数据库，不动ERP表。
- **已经执行过旧版中台DDL**：备份后查看`SHOW CREATE TABLE sibebid.adm_case_document;`，执行[升级DDL](../sql/adm-management-center-upgrade-v2.sql)，保留原payload及版本。此脚本执行一次；若已有部分生成列，核对后只补缺项，不重复整段执行。
- 两份不要都执行。CREATE IF NOT EXISTS不会自动升级旧表。生成列/索引升级可能占用资源，按实际数据量安排维护窗口；禁止用删表重建来解决升级错误。

用户提供的ERP DDL有38字段；Java当前实体43字段，额外的CNY金额、PNR、恢复时限、差异二级及申诉对象在该DDL中未见。新系统保留这些扩展字段，但历史缺失不补造。原`uk_adm_no`是普通CREATE INDEX，并非唯一约束；新系统以独立主键建档，历史以旧id防重，不按ADM号强行归并。

## 2. 配置及服务更新

若当前MYSQL连接本来就是该MySQL实例，只需在本项目服务端私密.env确认：

```dotenv
ADM_MYSQL_DATABASE=sibebid
```

其余未填的ADM_MYSQL_HOST/PORT/USER/PASSWORD沿用MYSQL_*，不是ERP_MYSQL_*。如果是另一个实例，必须单独配置完整ADM连接；不要发送密码到聊天或提交Git。账户需目标表SELECT/INSERT/UPDATE权限，建表由你或DBA执行；API不执行生产DDL。

在原data_report目录、沿用原Compose项目更新代码后重建：

```bash
git pull --ff-only
docker compose up -d --build api web worker
docker compose ps
```

worker需同步更新，才能导出新增字段与历史依据。保留1818/5160及已有卷；不要down -v。ADM附件和导入计划沿用`adm_data`卷，数据库与附件应配套备份。容器Started/Healthy不等于业务验收。

账号管理给专员/管理员配置ADM菜单及需要的查看、新建、编辑、分配、导入、导出、审核、财务确认、结案等功能；业务处理人至少有`adm.center`、`adm.view`、`adm.handle`。分配现在按已启用且具备ADM菜单/查看/处理权限的账号选择，不需要人工记账号ID，不自动创建旧Java用户或继承旧权限。

## 3. 首轮人工验收（建议按此顺序）

1. 管理员新建一张测试主单，底部＋三条订单：出/退/改，各写不同问题和处理计划。原金额不自动分给每条；保存、刷新核对说明、业务大类、编码、CNY金额、数量等仍独立存在。
2. 主单与每条订单分别上传材料，预览/下载核对归属。文件不共用一段URL备注替代；不同订单的申诉、恢复和结果不能串单。
3. 发布后勾选多条订单批量分配，业务人员在自己的范围接单、填写处理说明。失败项应有原因，不能因为批量按钮点过就显示全部成功；转单需填写原因。
4. 各订单按实际需要恢复/申诉，上传证据后提交，审核通过或退回。需要财务处理的由人工确认凭证，不需要的填写依据；不得把人工记录说成财务自动核验。父单结案仍检查明细、原件、审核和金额。
5. 下载统一两sheet模板试录两张主单及明细，先预览再导入；错误修正后重试。新增字段可选，旧模板缺列不清空已有数据。日常XLSX当前仅新单建档，不把它当覆盖已有单的批量更新工具。
6. 管理员试导一条脱敏历史JSON，确认历史原状态/原字段/旧id保留，不出现在活跃工作台，不继承旧锁/审核/付款。补传原件后仍为历史只读；同数据重复导入复用，同旧id内容变化报冲突。需要继续处理可引用新建，原档案不回写。

填写处理结果、实际上线/完成等事实不同于审批动作；不能靠编辑状态数字绕过既有结案门禁。当前差异一/二级支持独立填写，不调用Java旧字典接口；未知编码和名称需核实，不猜映射。

## 4. 后续历史迁移入口

在ERP数据库工具中**只读导出adm_records为UTF-8 JSON数组**（不是SQL文件），保留原主键id、字段名及原始值；大整数、金额建议以字符串导出，日期以明确的日期/时间字符串导出。支持snake_case或Java camelCase字段，缺失扩展字段留空，null不能替换为0。

格式示意（合成数据，不是实际业务）：

```json
[
  {"id":"10001","adm_no":"DEMO-ADM-01","supplier_code":"DEMO-SUP","supplier_type":3,
   "ota_code":"DEMO","ota_order_no":"DEMO-ORDER","currency":"CNY","total_amount":"100.00",
   "adm_status":3,"status":1,"remark":"仅为格式演示","resolution":"历史处理说明"}
]
```

上传入口：ADM台账→批量导入→选择.json→校验预览→确认导入。仅管理员允许历史归档；文件大小沿既有上传限制、每文件默认最多10000行。非法日期、负数金额等无法按当前模型安全映射时明确报错，先核对，不自动截断/取绝对值/填零；可分批处理。

按来源系统＋旧id全局防重，不依赖文件名、文件hash或导入管理员。一个旧来源行保留为一个档案，不根据同ADM号猜合并，不拆逗号串生成多订单组合；真正多订单关系须另行核实后使用中台模板录入。历史完整字段只读留存，导出另带“历史原始字段”sheet，超长不能无损放入Excel时拒绝而非截断。

旧附件地址不执行下载。可在历史主单管理员补传原件，保留文件hash、归属、版本和实际补传时间；这不证明旧地址所有文件都已迁移。独立Python恢复库、ERP外部操作日志及批量原件自动搬迁尚未实现，需其真实结构/来源再补，不能把原表的人员/时间字段当完整历史日志。

## 5. 错误、容量和切换边界

- 缺表、缺生成列、认证失败、无权限、目标库不存在、无法连接/连接中断分别显示固定错误码；不输出密码/主机/原SQL或供应商异常全文。网络未知先刷新核对，不盲目重复建单。
- “全部范围”台账已用SQL筛选/分页及索引，配置检查不再全量拉取业务数据；本人/团队仍复用原权限裁剪路径，后续规模扩大需进一步优化，不承诺百万级台账能力。主单JSON含历史审计会增长，正式容量和备份恢复需真实环境验收。
- 日常XLSX不覆盖旧单；历史变更冲突也不自动增量覆盖。此次交付不包含自动企微催办、ERP实时查询或自动财务匹配，不作为人工管理首轮验收前置。
- 人工验收前继续使用旧系统正式处理；演示数据不要与正式业务重复办理。切换前完整备份、旧系统停写、补齐增量并核对分币种金额/单量/状态/人员/附件，才开放新写入口。旧库只读留查，不同时双写。
- 失败回退先停新写，保留切换后新增记录，核对补回方案；不直接把旧版本API接到新增历史档案上写入，不删除新表/卷或覆盖备份。

本轮未执行生产DDL、ERP导出、真实迁移、服务器部署或群通知。代码检查不代替上述人工业务验收。
