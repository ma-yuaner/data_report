## 核实与认定状态

1. 自动通过/疑似问题等 → 人工核实“核查无问题” → 人工状态核查无问题；无原案例不额外造案例。
2. 任意自动结果 → 人工核实“有问题＋待咨询/已咨询” → 原子创建待认定案例并跳转跟进；状态有问题-待咨询/已咨询。
3. 待认定 → 核实无问题 → 已完成，只保留全部案例，既不在计入也不在不计入。
4. 待认定 → 计入差错 → 计入差错池；之后调整不计入 → 不计入差错池，保留前后认定依据，计入池不再出现。
5. 待认定问题不能直接点已完成，不能直接不计入差错；重新认定/完成前检查当前证据。证据变化时旧记录显示待重新核实。
6. 归档特殊案例不改变待认定/计入/不计入的业务认定；人工从特殊转首次时特殊标记取消。历史多单案例须从原案例统一调整；单单重核不能悄悄改其他订单。

V3每次写操作仍用原reviews/cases API、认证/CSRF/权限、幂等回执、版本和同事务事件。V3案例的规则由服务器保存的workflowVersion决定，客户端省略版本也不能绕过认定门禁。旧版接口/数据保留兼容；历史简版有问题但没有案例的订单，需重新核实一次生成案例，不在GET中自动写库或猜测迁移。

## 指标数据口径及发布

- 用户已确认：订单全部`order_info_issue.issue_profit`之和（CNY），不加佣金，不用关联订单均值，不用财务预估利润替代。任一票利润缺失或无出票明细则总利润NULL；真实0保留0。DECIMAL(28,4)，源需Decimal，不静默舍入超精度值，超精度/溢出拒绝发布。
- 航段按订单`order_info_segment.id`去重，仅airlift_flag=1计航空段；不存在航段或标记未知为NULL；已知全非航空为0。航司取订单出票明细marketing_airline去重，可多值，不复制利润。
- 业务部门通过同目标库出票核对表`order_no→org_cname`映射；可多归属，不凭平台/姓名推断责任。一个问题订单多部门分别计入，部门行不能相加成去重总量，缺归属单列“业务部门未同步”。这是业务部门分布，不是正式责任认定。
- 自动形成结论占比=(当前自动通过+疑似问题)/去重目录订单；自动通过、人工核实占比分别列出。证据过期人工记录不计为当前问题或当前差错；利润缺失组不发布合计，避免SUM忽略NULL冒充完整总量。
- 辅助指标与核查规则计算分开，本次不改核心规则、规则版本或ETL运行时SHA。指标快照只用于展示、筛选排序和分析，不覆盖自动核查结论。
