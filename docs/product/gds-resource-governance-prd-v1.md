# GDS/OTA 资源治理与查定比控制 PRD V1（开发基线）

- 文档状态：V1口径与首批数据表已确认，进入数据接入设计
- 更新日期：2026-10-14
- 产品归属：企业数据中台
- 业务负责人：数据部马远尔
- 本阶段范围：先完成日级查询事实、有效PNR分母与分析页面；规则、责任人、上下线闭环后续逐步建设

## 1. 背景

公司通过外部GDS与OTA接口完成查询、验价和生单。外部资源方会考核查询量与有效生单量的比例；查定比超过目标范围会产生费用或处罚。因此，数据部需要建立一套可分析、可预警、可处置、可追踪的资源治理系统，降低无效查询并持续验证治理效果。

当前内部月均查定比约为`5354:1`，阶段目标控制在`4000:1`以内，即压降约1400次无效查询/有效生单。目标值必须支持按GDS、PCC、平台或合同独立配置，不能写死在程序中。

## 2. 产品目标

系统需要连续回答五个问题：

1. 当前公司、GDS、PCC、平台的查定比和成功率是否达标？
2. 哪些资源贡献了最多无效查询，问题发生在哪个查询链路？
3. 哪条规则触发了异常，应该观察、限流、下线还是永久关闭？
4. 数据部是否已经打标，技术系统何时实际执行，业务是否提出恢复申请？
5. 执行后查定比、成功率与业务量是否改善，是否需要升级处罚？

最终目标不是提供另一张统计报表，而是形成以下闭环：

```text
接口调用数据
  → 分钟/小时/日指标
  → 异常识别与评分
  → 数据部确认控制标签
  → 技术系统执行上下线
  → 技术回执
  → 冷却期复测
  → 恢复 / 升级处罚 / 永久关闭
  → 管理复盘
```

## 3. 范围与边界

### 3.1 本系统负责

- 统一展示GDS与OTA查询、验价、生单链路指标；
- 按公司、平台、站点、GDS、PCC、航司、接口分组、时间等维度分析；
- 识别查定比、成功率、耗时和异常波动；
- 配置规则、评分和阶梯处置策略；
- 生成“观察、限制、临时下线、永久关闭”等控制标签；
- 将控制标签发送给技术系统并接收执行回执；
- 记录业务恢复申请、数据部审批及完整审计轨迹；
- 生成每日异常清单、治理效果和管理汇报。

### 3.2 本系统不负责

- 不直接调用生产交易系统执行拉黑或恢复；
- 不绕过技术系统直接修改GDS/PCC权限；
- 不在MySQL大宽表长期保存高体量航线级明细；
- 不把未确认的分母、成功状态或处罚规则作为正式口径；
- 第一版不做模型自动归因，所有“原因”必须来自规则证据、错误码或人工处理记录。

## 4. 已有数据链路

### 4.1 上游采集

接口调用日志由Kafka消费进入Hive ODS，保留1天：

| 来源 | 查询日志 | 验价/生单日志 |
|---|---|---|
| GDS | `ods_gdssearch_log_inc` | `ods_gds_verify_order_log_inc` |
| OTA | `ods_otasearch_log_inc` | `ods_ota_verify_order_pay_log_inc` |

ODS保留原始JSON与调用明细，用于短期追溯和数据补偿，不直接服务前端。

### 4.2 DWD标准明细

ODS清洗为列式存储的5分钟DWD，保留3天：

| 来源 | 查询明细 | 验价/生单明细 |
|---|---|---|
| GDS | `dwd_gds_search_carrierdata_5minute` | `dwd_gds_verify_carrierdata_5minute` |
| OTA | `dwd_ota_search_carrierdata_5minute` | `dwd_ota_verify_carrierdata_5minute` |

DWD负责JSON拆列、字段标准化、去重、状态归一和分钟级明细追溯。DWD与ODS业务事件一致，只是存储形式和查询效率不同。

### 4.3 DWS与服务层

DWS保留小时、日、月和常用维度聚合。历史表较多且割裂，后续需统一成“指标事实 + 维度”的标准模型，不继续为每个页面组合新增一张孤立表。

推荐服务结构：

```text
Hive ODS（1天原始）
  → Hive DWD（3天列式明细）
  → Hive DWS（分钟/小时/日统一指标）
  → MySQL ADS/BI（前端高频汇总与工作流）
  → 企业数据中台

航线等高基数明细：页面下钻时按短时间范围直接查询Hive DWD/DWS，不进入常驻MySQL大宽表。
```

V1首批MySQL服务表确定为：

| 表名 | 职责 | V1处理方式 |
|---|---|---|
| `sibebid.bi_ota_gds_request_day` | 保存OTA/GDS查询、验价、直连生单接口量及实际有效PNR | 复用现有表，新增`pnr_count`；不加入规则、责任人等流程字段 |

该表以`data_source=0/1`纵向区分OTA渠道层与GDS资源层，两个层级分别计算、禁止相加。目标值、规则、责任人和上下线状态必须保存在后续独立配置/流程表中，不能塞入事实表。

## 5. 核心口径

### 5.1 查定比

```text
查定比 = SUM(查询接口调用次数) / SUM(实际有效PNR数)

V1字段公式：
SUM(bi_ota_gds_request_day.search_request_count_all)
÷ SUM(bi_ota_gds_request_day.pnr_count)
```

- 查询次数按接口真实调用事件计数，必须先按请求唯一键去重；
- `order_request_success`只是直连生单接口成功次数，不代表最终形成有效PNR，不得作为正式查定比分母；
- “定”以实际有效PNR为准，必须按PNR唯一键去重；同一PNR多乘客、多航段不能重复计数；
- 有效PNR仍需技术确认状态、取消/作废回算规则与日期归属字段；
- 当有效PNR为0且查询量大于0时展示“∞/无有效PNR”，不能展示0；
- GDS与OTA链路应分别计算，也可在统一维度下汇总；
- 页面不得直接平均各明细行已有比率，必须使用汇总后的分子/分母重新计算。
- OTA与GDS的查询和PNR分别在各自`data_source`层内聚合；同一订单可同时服务两种观察视角，但不得跨层求和。

### 5.2 配套指标

- 查询请求量、查询成功量、查询成功率；
- 验价请求量、验价成功量、验价成功率；
- 生单请求量、直连生单接口成功量、实际有效PNR量；
- 平均/P95响应耗时；
- 缓存命中率、变价率、重复查询率；
- 目标允许查询量：`有效生单数 × 目标查定比`；
- 超额查询量：`MAX(查询量 - 目标允许查询量, 0)`；
- 压降率：`超额查询量 / 查询量`；
- 治理贡献：某资源超额查询量 / 公司总超额查询量。

### 5.3 当前待确认口径

1. “实际有效PNR”的来源表、唯一键、有效状态、日期字段及取消/作废是否扣回；
2. 查询去重使用请求ID、会话ID还是业务组合键；
3. 验价和生单是否在同一源表中通过事件类型区分；
4. GDS处罚目标是否统一为4000，还是按GDS/PCC合同配置；
5. 航段数是否参与查定比分母，或仅作为辅助分析指标。

## 6. 用户与权限

| 角色 | 主要职责 | 核心权限 |
|---|---|---|
| 数据运营经理 | 目标与规则管理、审批永久关闭/恢复 | 全部查看、规则发布、标签确认、审批、复盘 |
| 数据开发/分析 | 数据质量、异常诊断、规则草稿 | 查看、诊断、创建草稿、生成建议标签 |
| 业务部门经理 | 处理所属平台/PCC异常、提交说明与恢复申请 | 仅查看责任范围、填写处理、申请恢复 |
| 技术执行方/系统 | 消费控制标签并返回执行结果 | 读取待执行指令、写执行状态与时间 |
| 管理层 | 查看目标、趋势、治理效果 | 只读总览、汇报、效果复盘 |

责任范围通过“平台/GDS/PCC/部门/经理”映射维护。业务人员不得修改规则阈值或技术回执。

## 7. 菜单与页面

一级菜单建议为“资源治理”，本期先建设“GDS/OTA资源治理”，包含五个页面：

### 7.1 资源总览

- 公司当前查定比、目标值、差距、超额查询量；
- 查询→验价→生单链路转化；
- 小时/日/月趋势；
- GDS、PCC、平台、航司、接口分组维度切换；
- 默认按超额查询贡献降序；
- “分析此项”进入右侧工作区，继续查看日汇总、异常记录和短期Hive明细。

### 7.2 异常事件

- 每日自动汇总异常；
- 事件等级、资源对象、指标、当前值、阈值、影响量、负责人、状态；
- 支持确认、观察、提交说明、生成标签、申请恢复；
- 相同“规则 + 资源对象 + 异常类型”持续异常只更新同一事件；
- 连续恢复达到规则要求后进入待复核或自动恢复。

### 7.3 规则与评分

- 目标规则：查定比、成功率、耗时、重复查询、请求突增；
- 适用范围：公司、来源、平台、GDS、PCC、航司、接口分组；
- 触发条件：阈值、连续窗口、最小样本量、冷却时间；
- 评分维度：超标幅度、影响请求量、持续时长、历史次数；
- 动作映射：提醒、观察、限流、临时下线、永久关闭建议；
- 草稿、启用、暂停、版本历史和操作审计。

### 7.4 上下线工单

- 数据部只生成控制标签/指令，不直接执行生产拉黑；
- 展示待技术执行、执行中、已执行、执行失败、已到期、待恢复；
- 记录标签、限制级别、计划时间、实际执行时间、技术回执和失败原因；
- 临时限制到期后自动进入复测窗口，不直接视为治理成功；
- 永久关闭后的业务恢复必须提交申请，由数据运营经理审批。

### 7.5 治理复盘

- 本期查定比与目标完成度；
- 异常、限制、恢复和永久关闭数量；
- 治理前后查询量、生单量、成功率和查定比变化；
- 各部门、平台、GDS/PCC治理贡献；
- 未按时处理、重复违规和技术未执行列表；
- 一键形成每日简报和管理汇报。

## 8. 异常与处置流程

### 8.1 事件状态

```text
待确认 → 观察中 → 待打标 → 待技术执行 → 限制中 → 复测中
                                             ├→ 已恢复
                                             └→ 再次异常 → 升级处罚
```

业务可提交“测试中，申请延后观察”等说明，但只能改变观察截止时间，不能自行关闭异常。

### 8.2 阶梯策略

默认演示策略如下，正式值由规则配置：

| 违规次数 | 建议动作 | 限制时长 | 恢复条件 |
|---:|---|---:|---|
| 1 | 提醒并观察 | 30分钟 | 连续2个窗口达标 |
| 2 | 临时下线 | 1小时 | 到期后复测达标 |
| 3 | 升级下线 | 4小时 | 到期后复测达标 |
| 4 | 强化限制 | 24小时 | 数据部复核通过 |
| 5及以上 | 永久关闭建议 | 长期 | 业务申请 + 数据部审批 |

策略必须支持按资源类型覆盖。升级依据是规则版本与历史命中次数，不能由前端临时计算。

### 8.3 防抖与恢复

- 达到最小请求量后才判断比例；
- 连续N个5分钟窗口异常才生成事件；
- 已有未关闭事件不重复创建；
- 限制后进入冷却期，避免频繁上下线；
- 连续N个窗口恢复才允许恢复；
- 规则变更后保留旧版本证据，历史事件不被新规则改写。

## 9. 数据对象（概念模型）

V1复用统一OTA/GDS日汇总表并增加实际有效PNR字段；后续治理闭环再逐步补充以下对象：

| 对象 | 用途 |
|---|---|
| 统一资源指标事实 | 保存5分钟/小时/日分子、分母与成功率基础量 |
| 资源维度字典 | 统一GDS、PCC、平台、站点、航司、接口分组编码 |
| 责任人映射 | 资源对象对应部门、经理和通知人 |
| 规则/规则版本/条件 | 配置阈值、评分、连续窗口和动作 |
| 异常事件/事件日志 | 幂等记录异常生命周期与人工处理 |
| 控制标签 | 数据部确认的观察、限流、下线或恢复标签 |
| 技术执行工单/回执 | 记录发送、执行结果、实际时间和错误信息 |
| 恢复申请 | 业务说明、申请范围、审批结果与有效期 |
| 效果快照 | 保存动作前后窗口指标，支持复盘 |
| 通知发件箱 | 站内/企业微信可靠通知和失败重试 |

## 10. API边界（正式开发阶段）

- 总览查询：返回目标、KPI、趋势与完整维度排序；
- 单项诊断：返回所选资源的链路指标、规则证据和异常历史；
- 日汇总/明细：短范围查询Hive，限制日期、分页和最大行数；
- 规则管理：草稿、校验、发布、暂停和版本查询；
- 事件处理：确认、延后观察、生成标签、填写处理结果；
- 控制工单：发布给技术、查询状态、接收幂等回执；
- 恢复申请：创建、审批、驳回、执行恢复；
- 管理汇报：按日/月生成汇总，不直接导出ODS/DWD全量明细。

所有写接口必须记录操作者、时间、前后值和请求ID；技术回执必须支持幂等。

## 11. 数据与性能要求

- ODS保留1天，DWD保留3天的现状不变；
- 前端默认查询MySQL汇总，不扫描ODS/DWD；
- 航线、错误码和调用明细只在下钻时按短时间范围查询Hive；
- 5分钟指标任务只处理新增窗口，禁止每5分钟全量重算；
- 页面汇总建议5分钟级更新，日/月结果可异步固化；
- 规则计算使用统一特征表，一批数据匹配全部生效规则，不为每条规则单独写ETL；
- 明细下钻必须设置日期上限、分页、超时和并发限制；
- 缺数据、真实0和分母为0必须分别展示。

## 12. 通知原则

- 新异常、升级处罚、技术执行失败、观察到期、恢复申请超时需要通知；
- 通知接收人由责任人映射和花名册确定，不在规则中重复填写人员ID；
- 企业微信消息只展示最小必要信息，详情通过中台链接查看；
- 相同事件在冷却期内不重复轰炸；
- 所有站内、站外通知进入可靠发件箱并保留发送结果。

## 13. 验收标准

1. 能从公司总览下钻到平台、GDS、PCC，并看到同口径日汇总；
2. 查定比由汇总分子/分母计算，不直接平均比例；
3. 能识别超过目标且达到最小样本量的资源，并生成唯一异常事件；
4. 同一事件能完成观察、打标、技术执行、回执、复测和恢复/升级；
5. 技术未执行时页面不能显示“已下线”；
6. 业务只能处理责任范围并提交申请，不能自行修改规则或关闭限制；
7. 管理层能查看目标差距、超额查询贡献、重复违规和治理效果；
8. 航线明细不进入常驻大宽表，短期下钻可追溯到Hive证据；
9. 所有规则、标签、审批和回执有完整审计记录；
10. 数据延迟或来源缺失时明确提示，不能将缺失展示为0。

## 14. 开发前置依赖

正式开发前需要业务/数据/技术补齐：

1. 实际有效PNR来源表DDL与脱敏样例数据；
2. PNR唯一键、有效状态、取消/作废处理规则和日期归属字段；
3. 查询请求唯一键，以及请求事实与PNR事实的公共维度映射；
4. GDS、PCC、平台、航司、接口分组字段映射；
5. 各资源正式目标值、最小样本量、处罚阶梯和恢复条件；
6. 平台/GDS/PCC到部门经理的责任映射来源；
7. 技术系统消费控制标签与返回回执的接口协议；
8. 企业微信通知群、消息模板与升级通知对象；
9. 现有小时/日/月DWS表清单与口径，决定复用或收敛；
10. 外部处罚规则或合同口径，用于确认目标是否允许资源级覆盖。
